# 공개 전 검증 기록

공개하기 전에 이 저장소를 새 디렉터리에 클론하고, `.env`만 채운 상태에서 스크립트가 게시한 결과를 다시 만드는지 확인했습니다.

- 일시: 2026-10-31
- 장비: GB10 1대 (aarch64, 통합 메모리 128GB)
- 이미지: `vllm/vllm-openai:v0.31.0`, 도구 이미지 `docker/tools.Dockerfile`
- 모델: EXAONE-4.5-33B-FP8 리비전 `69570ad5`. 33GB라 다시 받지 않고 기존에 받아 둔 사본을 `MODEL_DIR`로 지정했습니다.
- 원본 데이터: 모두 새로 받았습니다. AI Hub 키는 `.env`에 적지 않고 실행할 때 환경 변수로만 넘겼습니다.

전체 재현(생성 약 5.5시간, 학습 약 6.3시간)은 다시 돌리지 않았습니다. 대신 게시한 실행의 생성 데이터와 체크포인트를 검증용 기준 자료로 두고, 각 단계가 같은 입력에서 같은 출력을 내는지 확인했습니다.

## 같은 조건에서 세 구성 비교

개선이라고 말하려면 비교 대상도 같은 날, 같은 조건으로 재야 해서 MTP 없음, 원래 헤드, 새 헤드를 연달아 측정했습니다.

**모델 동일성.** `MODEL_DIR`의 22개 파일을 Hugging Face의 현재 배포본(main = `69570ad5`, 2026-10-31 확인)과 대조했습니다. LFS 파일은 SHA-256, 나머지는 git blob 해시가 모두 같았고 그 밖의 파일은 없었습니다. MTP 없음과 원래 헤드는 이 체크포인트를 그대로 썼습니다. 새 헤드의 서빙 디렉터리는 샤드 9를 뺀 모든 파일이 원본과 같은 inode이고, 샤드 9의 텐서 174개 중 `mtp.*`가 아닌 156개는 원본과 비트 단위로 같습니다. MTP 텐서 19개 중 18개가 바뀌었고, `mtp.norm.weight`는 학습 후에도 bf16 값이 그대로였습니다.

**조건.** GB10, vLLM v0.31.0, `GPU_MEM_UTIL=0.55`, `MAX_NUM_SEQS=1`, `CUDAGRAPH_MAX_SIZE=24`, MTP 드래프트 3개. `bench.sh LABEL off 2`와 `on 2`(프롬프트 5개 × 2회, 최대 400토큰, 기본 샘플링). 서버를 띄운 직후 첫 요청부터 측정했습니다. 수용률은 10개 요청의 수용 토큰 합 ÷ 드래프트 토큰 합입니다. 스텝당 토큰은 1 + 수용 토큰 ÷ (드래프트 토큰 ÷ 3)으로, 검증 한 번에 나아간 토큰 수입니다(상한 4).

비추론에서는 원래 헤드가 드래프트를 거의 전부 거부당해 MTP 없음보다 15% 느렸고, 새 헤드는 다섯 프롬프트 모두에서 두 구성보다 빨랐습니다. 추론에서는 새 헤드가 원래 헤드보다 수용률 0.5%p, 속도 0.5% 낮았습니다. 프롬프트별로는 한국어 대화와 문서 요약에서 높고 코드 리뷰(−3.8%p)와 코드 생성(−2.0%p)에서 낮았습니다. RTX PRO 6000에서 게시한 값(28.3% → 27.2%)도 같은 방향입니다.

새 헤드의 비추론 측정은 같은 날 두 번(이 비교와 위 GPU 단계 표) 했는데, 요청별 드래프트 수와 수용 수까지 같았습니다.

## 확인하지 않은 것

- 생성부터 학습까지의 전체 재현. 생성은 동시 요청 96개를 배치로 처리하므로 답변 토큰이 게시한 실행과 같다는 보장이 없습니다. [재현 절차](reproduce.md)의 기준값과 비교해 주세요.
- x86_64와 RTX PRO 6000에서 이 스크립트 실행. 블로그에 실은 RTX PRO 6000 수치는 같은 vLLM 이미지와 같은 서버 인자로 측정했지만, 이 저장소의 스크립트로 다시 돌리지는 않았습니다.
- `SERVER_MODE=external`(원격 서버)과 `VLLM_API_KEY`. 코드 경로는 같은 `curl`/`aiohttp` 호출이지만 이번 검증에서는 로컬 서버만 썼습니다.
- `analyze.sh eval`. 같은 `--eval-only` 경로를 `regime`과 stage2 시작 평가로 확인했습니다.
